01 — Problem → solution

The problem → the solution

source: project write-up
before · the problem

  1. ✕
    Two channels had to share one cart and one checkout, while stock, checkout and order flows stayed separate per seller.
  2. ✕
    Stock is limited per variant. Two buyers must never both get the last unit, but idle carts should not lock stock either.
  3. ✕
    Provider confirmation is asynchronous. It can arrive late (after the buyer cancelled), twice, or not at all.
  4. ✕
    One checkout can include orders from several sellers, and each can be cancelled or refunded on its own.
after · the solution

  1. 01
    A seller onboarding and catalog module with up to two variant axes per product and a price and stock row per variant.
  2. 02
    A cart extended with a channel flag so both channels coexist in one basket.
  3. 03
    Stock is held when the buyer opens the checkout summary, not when they add to cart, and released when they leave or the hold expires.
  4. 04
    One checkout session groups child orders, one per seller, under one checkout.
  5. 05
    Cancel, provider confirmation and a background check all go through the same locked path, so the order ends in one consistent state whichever arrives first.
  6. 06
    A per-seller order lifecycle with cancellation, return and refund cases, and seller income credited only after a buffer period.

01

Overview

+

The client already ran a marketplace app with its own catalog, accounts and cart. They wanted a second channel where independent sellers open shops and sell their own products, inside the same app, the same cart and the same checkout. I designed the channel end to end (approved by my lead) and wrote most of its core services.

What already existed (team / platform): buyer accounts and addresses, category tree, authentication, admin panel shell, media library, and the original channel's orders. Some later moderation features on shops (suspensions, visibility rules) were added by a colleague.

02

Engineering highlights

+

Stock correctness under concurrency: row locks on the variant before checking availability; a separate held counter, so on-hand stock only changes when an order is really paid or returned; a fixed lock order (variant, then hold) everywhere.

Late and duplicate checkout events: cancel asks the checkout provider first and does not cancel if the provider is unreachable; a late confirmation revives a cancelled checkout instead of losing a paid order; a duplicate confirmation does nothing; a background check recovers checkouts whose confirmation never arrived.

Idempotent refunds: every refund and restore step checks whether it already ran, so retries and double clicks are safe. A shared checkout is marked partially refunded while other orders in the same checkout are still paid.

Explicit state machines for shops, holds, orders, refunds and return cases, with a status history per order.

Scheduled jobs that cannot overlap, and seller income credited once with a timestamp guard.

03

Result

+

The full flow from seller onboarding to checkout, fulfilment and refunds went live. I handed it over after delivery and the team continues to run and extend it.
